# Архитектура приложения

## Общая модель

«Что приготовить?» состоит из модульного монолита на Java и Spring Boot и
отдельного frontend-приложения на React. Backend использует одну базу
PostgreSQL, а Java-код разделён по функциональным областям. Такое устройство
сохраняет простую модель данных и не смешивает каталог, избранное, историю и
другие сценарии в одном общем слое.

Работающий пользовательский интерфейс пока реализован на Spring MVC и
Thymeleaf. Независимый React-клиент получает и фильтрует каталог через
`GET /api/recipes`, загружает варианты фильтров через
`GET /api/recipes/filter-options` и показывает карточку через
`GET /api/recipes/{id}`. Избранное переключается через `PUT` и `DELETE` по
адресу `/api/recipes/{id}/favorite`, а отдельная коллекция загружается через
`GET /api/recipes/favorites`. Клиентские маршруты обслуживает React Router.
Остальные сценарии подключаются постепенно, а Thymeleaf сохраняется до
функционального паритета.

Frontend и backend собираются независимо, но это не разделение бизнес-логики на
микросервисы. Spring Boot остаётся единственным владельцем правил предметной
области и доступа к PostgreSQL.

## Структура репозитория

```text
what-to-cook
├── frontend/                 # React, TypeScript, Vite и shadcn/ui
├── src/main/java/            # backend и бизнес-логика
├── src/main/resources/       # Thymeleaf, миграции и ресурсы backend
├── src/test/                 # тесты Spring Boot
└── docs/                     # спецификация, архитектура и ADR
```

Во время разработки Vite запускается на порту `5173` и проксирует запросы с
префиксами `/api`, `/images` и `/user-images` в Spring Boot на порту `8080`.
Так React получает API и изображения через один origin без локальной настройки
CORS. Такая граница совпадает с будущей схемой размещения, где статические
файлы frontend и backend смогут работать в разных контейнерах за единым
reverse proxy.

## Структура Java-кода

Код группируется сначала по функциональности, а внутри функциональности — по
технической роли:

```text
io.github.baikoff.whattocook
├── home            # стартовая страница
├── assistant       # подбор блюда и веб-сценарий помощника
├── recipe          # рецепты, каталог, поиск и подбор
│   ├── domain      # сущности и бизнес-значения
│   ├── repository  # доступ к данным и спецификации запросов
│   ├── service     # сценарии приложения и их модели
│   └── web         # контроллеры и веб-валидация
├── favorite        # избранные рецепты
├── history         # история приготовления
├── pantry          # личный набор продуктов базовой кладовой
├── restriction     # ограничения по ингредиентам
├── telegram        # Telegram-адаптер, Bot API и long polling
├── image           # хранение и выдача изображений
└── common          # общие компоненты веб-слоя
```

Общий пакет `utils` намеренно не используется. Вспомогательный код размещается
рядом с функциональностью, которой он принадлежит. В `common` попадают только
компоненты, у которых действительно несколько независимых потребителей.

## Ответственность слоёв

### Web

Контроллер принимает HTTP-запрос, преобразует пользовательский ввод, вызывает
сервис и выбирает представление или перенаправление. В контроллере не должны
находиться расчёты, запросы к JPA-репозиториям и правила предметной области.

Web-валидация отвечает за понятные пользователю ошибки формы. Правило, которое
важно независимо от интерфейса, должно находиться в domain или service.

### Service

Сервис реализует пользовательский сценарий, координирует доменные объекты,
репозитории и внешние технические компоненты. Граница транзакции обычно
находится здесь.

Сервис не должен зависеть от HTML-шаблонов и деталей HTTP.

### Domain

Domain содержит сущности, перечисления, значения и чистые бизнес-правила.
Логику, которую можно выразить без Spring, базы и HTTP, предпочтительно держать
на этом уровне и проверять быстрыми unit-тестами.

### Repository

Repository отвечает за сохранение и выборку данных. Сложные фильтры и запросы
проверяются интеграционными тестами с PostgreSQL.

## Структура frontend-кода

`frontend/src/components/ui` содержит исходный код компонентов shadcn/ui.
Это не закрытая библиотека: компоненты принадлежат проекту и могут изменяться
вместе с визуальным языком приложения. Общие вспомогательные функции находятся
в `frontend/src/lib`, включая формирование адресов ещё не перенесённых страниц
backend. Код каталога расположен в `frontend/src/features/recipes`: отдельно
описаны типизированные API-клиенты и компоненты каталога и карточки рецепта.
Общий layout расположен в `frontend/src/components/layout`, а React Router
связывает каталог с адресом `/recipes/{id}` без перезагрузки документа.

Новые пользовательские сценарии frontend проверяются снаружи через React
Testing Library и Vitest. По мере переноса функций код будет группироваться по
предметным областям, а не в одну общую папку компонентов.

## Данные и миграции

PostgreSQL является основной и тестовой СУБД. Схема базы изменяется только
последовательными миграциями Flyway из `src/main/resources/db/migration`.
Hibernate работает в режиме проверки схемы и не создаёт и не обновляет её.

Уже применённая миграция считается неизменяемой. Исправление схемы или
начальных данных оформляется новой миграцией, чтобы существующая локальная база
могла обновиться тем же способом, что и чистая база.

Интеграционные тесты используют отдельный PostgreSQL через Testcontainers.

Базовая кладовая хранится в отдельной таблице `pantry_ingredients`, а не как
флаг у ингредиента. Принадлежность к кладовой является пользовательской
настройкой, а не постоянным свойством продукта. При появлении нескольких
пользователей такую связь можно будет дополнить владельцем без изменения
модели ингредиентов и рецептов.

## Изображения

Пользовательские изображения хранятся вне базы в
`data/images/recipes/{recipeId}/`. PostgreSQL хранит относительные пути и
связанные метаданные. Каталог пользовательских изображений исключён из Git.

Встроенные обложки хранятся в статических ресурсах приложения. В базе такой
путь имеет префикс `bundled:`, который преобразуется в URL `/images/...`.
Пути без этого префикса относятся к пользовательскому хранилищу и выдаются
через `/user-images/...`. Операции удаления применяются только к
пользовательским файлам.

Фотографические обложки классических рецептов нормализуются до JPEG 1200×800
с качеством около 85% и целевым размером до 500 КБ. Единое соотношение сторон
делает кадрирование предсказуемым в каталоге и на странице рецепта.

Операции замены должны быть устроены так, чтобы ошибка сохранения рецепта не
привела к преждевременной потере предыдущего изображения.

## Внешние интерфейсы

Внешними границами являются серверный веб-интерфейс, REST API для React-клиента
и Telegram-адаптер. `GET /api/recipes` возвращает неархивированные рецепты с
обложкой, основными характеристиками, признаком избранного и предупреждениями
об ограничениях. Необязательные query-параметры преобразуются в существующий
`RecipeSearchCriteria`, поэтому web- и REST-интерфейсы используют одни правила
поиска. `GET /api/recipes/filter-options` возвращает значения перечислений и
справочников базы, необходимые React-форме. `GET /api/recipes/{id}` возвращает
полную карточку: ингредиенты, замены, шаги, изображения, ограничения, источник
и видео. Необязательный параметр `servings` передаётся в существующий
`RecipeCatalogService`, поэтому пересчёт количества остаётся бизнес-правилом
backend, а не React-компонента.
`GET /api/recipes/favorites` использует `RecipeCatalogService.getFavorites()` и
возвращает тот же DTO карточек, что и основной каталог. Поэтому каталог и
избранное переиспользуют один React-компонент карточки и одинаково отображают
обложку, ограничения и основные характеристики рецепта.
`PUT /api/recipes/{id}/favorite` добавляет рецепт в избранное, а `DELETE` по
тому же адресу удаляет его. REST-контроллер модуля `favorite` переиспользует
`RecipeFavoriteService`: правила существования и доступности рецепта остаются в
сервисном слое, а React обновляет локальное состояние только после успешного
ответа backend.
Telegram-бот получает обновления через long polling и обращается к официальному
Bot API через Spring `RestClient`. Он переиспользует сервисный слой, не
дублирует бизнес-логику и не обращается напрямую к JPA-репозиториям.

Обычные команды и нажатия inline-кнопок преобразуются в единую входную модель.
Для `callback_query` клиент вызывает `answerCallbackQuery`, а действие
`SURPRISE` передаётся адаптеру рекомендаций. Адаптер использует существующий
`DishRecommendationService`, выбирает первый результат случайной подборки и
преобразует его в Telegram-сообщение. Поэтому правила архива, ограничений и
приоритета ещё не приготовленных блюд одинаковы в веб-интерфейсе и боте.

Для подбора по продуктам Telegram-адаптер временно хранит состояние диалога по
`chatId`: ожидание списка, найденные рекомендации и номер текущего варианта.
Список из сообщения преобразуется в идентификаторы общего справочника, после
чего передаётся в тот же `DishRecommendationService` с целью
`USE_PRODUCTS`. Состояние намеренно не сохраняется в PostgreSQL: на локальном
однопользовательском этапе потеря незавершённого диалога после перезапуска
допустима. Перед публичным многопользовательским развёртыванием это решение
нужно пересмотреть.

Для рекомендации с обложкой Telegram-адаптер читает изображение через единый
компонент, который понимает оба используемых приложением источника:
`/images/...` для встроенных ресурсов и `/user-images/...` для пользовательского
хранилища. Файл передаётся в Bot API методом `sendPhoto` как multipart-запрос,
поскольку Telegram не может обратиться к локальному URL приложения. Текст
рекомендации становится подписью к фотографии и ограничивается лимитом Telegram
в 1024 символа. Если изображение отсутствует, повреждено или имеет
неподдерживаемый формат, адаптер сохраняет основной сценарий и отправляет
рекомендацию методом `sendMessage`.

Telegram-модуль создаётся только при включённой настройке
`app.telegram.enabled`. Токен не хранится в репозитории, а доступ ограничивается
настраиваемым списком числовых Telegram ID. Причины выбора прямого Bot API
зафиксированы в [ADR 0001](decisions/0001-прямой-доступ-к-telegram-bot-api.md).

REST-контроллеры становятся ещё одним входным адаптером над теми же сервисными
сценариями приложения. Они не должны дублировать бизнес-логику или обращаться к
HTML-представлениям. На первом этапе API предназначен для собственного
React-клиента и не объявляется публичным контрактом для сторонних интеграций.

## Проверка архитектуры

Архитектурное решение считается соблюдённым, если:

- бизнес-логика не находится в контроллерах и шаблонах;
- контроллеры обращаются к сервисам, а не реализуют сценарий самостоятельно;
- изменение схемы оформлено новой миграцией Flyway;
- новая функциональность размещена в своей предметной области;
- React-клиент получает данные через `/api` и не обращается к PostgreSQL;
- REST-контроллеры переиспользуют сервисный слой backend;
- тест выбран по назначению согласно
  [стратегии тестирования](testing-strategy.md).

Значимые изменения направления фиксируются отдельной записью в
[`docs/decisions`](decisions/README.md).
