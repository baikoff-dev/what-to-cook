# Стратегия тестирования

## Назначение

Проект разрабатывается небольшими вертикальными срезами по подходу
Outside-In TDD. Для каждой новой функции сначала описывается наблюдаемое
пользовательское поведение, затем создаётся падающий тест на внешней границе
приложения и только после этого появляется реализация.

Цель подхода — проверять не внутреннее устройство классов, а полезное для
пользователя поведение. Внутренние unit-тесты добавляются там, где они помогают
быстро разрабатывать и объяснять нетривиальные бизнес-правила.

## Рабочий цикл

Каждая функция проходит следующие этапы:

1. **Исследование.** Определить существующее поведение, затрагиваемые модули и
   уже имеющиеся тесты. Код на этом шаге не изменяется.
2. **Сценарий.** Согласовать одно поведение в форме «Дано / Когда / Тогда» и
   критерии завершения.
3. **RED.** Добавить минимальный внешний тест и убедиться, что он падает по
   ожидаемой причине. Production-код пока не изменяется.
4. **GREEN.** Реализовать минимальный вертикальный срез, необходимый для
   прохождения теста. При наличии сложных правил добавить быстрые внутренние
   тесты.
5. **REFACTOR.** Улучшить имена, структуру и устранить дублирование, не меняя
   поведение и сохраняя тесты зелёными.
6. **Проверка.** Запустить новый тест, связанные тесты и затем полный набор
   тестов. Просмотреть diff и при необходимости обновить документацию.

Во время обучения после этапа RED агент останавливается, показывает созданный
тест и объясняет причину падения. Переход к реализации выполняется после
подтверждения пользователя.

## Уровни тестов

### Acceptance-тесты

Acceptance-тест описывает пользовательский сценарий через публичную границу
приложения. Для текущего веб-интерфейса такой границей является HTTP.

Тест запускает Spring Boot на случайном порту, использует PostgreSQL через
Testcontainers и проверяет ответ так, как его наблюдает пользователь. Он может
подготовить данные через тестовую фикстуру, но основное действие сценария
должно выполняться через HTTP.

Имена новых классов: `*AcceptanceTest`.

Acceptance-тест не должен проверять точную HTML-разметку, CSS-классы и другие
детали представления, если они не являются частью согласованного поведения.
Предпочтительны проверки статуса ответа, перехода, видимого текста и доступных
пользователю действий.

### Интеграционные тесты

Интеграционный тест проверяет совместную работу нескольких технических
компонентов: Spring-конфигурации, JPA-запроса, репозитория, миграции Flyway или
PostgreSQL-ограничения.

Имена классов: `*IntegrationTest`.

Для поведения, зависящего от SQL, связей JPA или особенностей PostgreSQL,
используется настоящий PostgreSQL через Testcontainers, а не база H2.

### Unit-тесты

Unit-тест проверяет один бизнес-компонент без запуска Spring. Он подходит для
расчётов, ранжирования, правил ограничений, переходов состояний и другой
нетривиальной логики.

Имена классов: `*Test`. Такой тест должен оставаться быстрым и не обращаться к
сети, файловой системе или базе данных.

Не требуется создавать unit-тест для каждого метода, простого конструктора,
getter или стандартной работы Spring Data JPA.

## Правила тестовых данных

- Тест самостоятельно создаёт или явно выбирает необходимые данные.
- Данные одного теста не должны делать другой тест зависимым от порядка запуска.
- Для повторяющейся подготовки используются небольшие fixture/builder-классы.
- Очистка созданных данных выполняется надёжно, в том числе при падении теста.
- Тестовые данные должны объяснять сценарий, а не копировать весь production-каталог.
- Уже применённые миграции Flyway не изменяются ради теста.

## Команды

Полный набор тестов в Windows:

```powershell
.\mvnw.cmd test
```

Один класс:

```powershell
.\mvnw.cmd -Dtest=RecipeVideoLinkAcceptanceTest test
```

Один тестовый метод:

```powershell
.\mvnw.cmd -Dtest=RecipeVideoLinkAcceptanceTest#classicRecipeShowsVideoLink test
```

Для интеграционных и acceptance-тестов Docker Desktop должен быть запущен.
Поднимать PostgreSQL из `compose.yaml` вручную не требуется: тесты используют
отдельный контейнер Testcontainers.

## Работа с ИИ как с pair programmer

Пользователь определяет ожидаемое поведение, принимает продуктовые решения и
подтверждает переход между этапами. Агент исследует код, предлагает сценарий,
пишет тест и реализацию, запускает проверки и объясняет технические решения.

Агент обязан:

- не придумывать неоднозначные требования без согласования;
- не писать production-код до получения ожидаемого RED;
- не удалять и не ослаблять тест только ради GREEN;
- реализовывать один небольшой сценарий за цикл;
- показывать причину падения и результаты проверок;
- отделять обязательные изменения от возможных улучшений;
- не создавать commit и не выполнять push без отдельного запроса.

## Критерии завершения функции

Функция считается завершённой, когда:

- согласованный пользовательский сценарий реализован;
- внешний тест проходит;
- нетривиальные внутренние правила покрыты подходящими тестами;
- связанные и полные тесты проходят;
- diff не содержит несвязанных изменений;
- документация обновлена, если изменились поведение, архитектура или запуск.
