# Отдельное frontend-приложение

Статус: принято

## Контекст

Работающий веб-интерфейс построен на Spring MVC и Thymeleaf. Он позволил быстро
проверить сценарии приложения, но дальнейшее развитие адаптивного и более
интерактивного интерфейса удобнее вести с современным клиентским стеком.

При этом бизнес-логика уже разделена по областям в модульном монолите. Её
перенос в микросервисы не решает задачу интерфейса и преждевременно усложнит
локальный запуск, транзакции и тестирование.

## Решение

- Создать в том же репозитории отдельное приложение `frontend` на React,
  TypeScript и Vite.
- Использовать Tailwind CSS и shadcn/ui. Исходный код выбранных компонентов
  хранить в проекте, чтобы визуальная система не зависела от закрытой темы.
- Оставить Spring Boot модульным монолитом и единственным владельцем
  бизнес-логики и PostgreSQL.
- Передавать данные между frontend и backend через REST API с префиксом `/api`.
- В локальной разработке запускать Vite на порту `5173` и проксировать `/api`
  в Spring Boot на порту `8080`.
- Сохранять Thymeleaf до тех пор, пока React-клиент не достигнет функционального
  паритета по переносимому сценарию.
- В будущем собирать и размещать frontend и backend независимо, первоначально
  в рамках одного Docker Compose.

## Альтернативы

### Продолжить развивать только Thymeleaf

Это сохранило бы один процесс и минимальное количество инструментов, но дало бы
меньше практики современного frontend и усложнило бы создание богатого
клиентского взаимодействия.

### Встроить React-сборку в ресурсы Spring Boot

Один исполняемый файл упростил бы размещение, но связал бы жизненные циклы двух
частей и затруднил независимую разработку и контейнеризацию.

### Сразу разделить backend на микросервисы

Такое разделение не требуется текущим масштабом и добавило бы сетевые контракты,
распределённые транзакции и эксплуатационную сложность без пользовательской
пользы.

## Последствия

- Для локальной разработки нужны Node.js и два процесса: Vite и Spring Boot.
- Появляется отдельный набор frontend-проверок: lint, Vitest и production build.
- Backend должен предоставить устойчивые REST-контракты над существующим
  сервисным слоем.
- На время постепенного переноса два интерфейса будут существовать параллельно.
- Frontend можно развивать и размещать независимо, не превращая предметные
  модули backend в микросервисы.
